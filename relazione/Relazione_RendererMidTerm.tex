\begin{center}\large\textbf{Abstract}\end{center}
\vspace{-4pt}
\begin{list}{}{\setlength{\leftmargin}{1.5em}\setlength{\rightmargin}{1.5em}}\item[]
\small\itshape
  Rasterizing large numbers of alpha-blended, depth-ordered 2D primitives is a core building
  block of real-time and offline rendering, and it is easily parallel in principle but
  easy to implement inefficiently. This report presents a CPU-only 2D circle rasterizer,
  implemented in Python with Numba, that draws $N$ alpha-blended circles onto an $H\times W$
  image using the painter's algorithm. Parallelism comes from Python threads
  running on the free-threaded (GIL-free) build.
  Four kernels of increasing complexity are compared:
  a sequential baseline, a naive per-pixel parallel kernel, a tile-based parallel kernel with
  bounding-box culling, and a tile-based kernel additionally written for auto-vectorization
  (branchless SIMD inner loop). On a 4-core / 8-thread AMD Ryzen~5 2400G, the tiled, vectorized
  kernel reaches a maximum speedup of \tbd{S$_{\max}$} over the sequential baseline (on
  \tbd{p} threads), while a dedicated scalar-vs-SIMD comparison shows vectorization
  alone contributes roughly \tbd{X$\times$} at a fixed thread count. A broader set of
  micro-benchmarks additionally isolates the effect of resolution, circle count, tile size,
  scheduling strategy, memory layout (SoA vs.\ AoS) and weak scaling, providing a systematic picture of where the
  performance comes from and where it saturates.
  \end{list}

\section{Introduction}

This report presents the design, implementation and performance analysis of a
sequential and parallelized 2D circle rasterizer. The project was developed to demonstrate how coarse-grained
multithreading and fine-grained vectorization can be combined to accelerate a
classic computer-graphics workload.

\subsection{Problem Description and Motivation}

Rasterization is the process of converting geometric elements into pixels.
This project targets a deliberately simple but representative primitive set:
$N$ circles, each defined by a 2D center, a depth coordinate $z$, a radius, an
RGB color and an alpha value (opacity). Circles are composited onto the image
using the \emph{painter's algorithm}: they are sorted by increasing depth and
drawn back-to-front, blending each new circle onto the frame buffer with the
standard ``over'' operator
\[
  \text{out} = \text{src}_{\text{rgb}}\cdot a + \text{dst}_{\text{rgb}} \cdot (1-a).
\]
The name comes from the way a painter works: the background is painted
first and nearer objects are painted over it, so whatever is closer covers
whatever lies behind, without a depth buffer. With transparency the order
is essential, because the ``over'' operator is not commutative: two
overlapping circles blended in opposite orders give different colors.
This is the same compositing model used by real rendering pipelines (e.g.\
particle systems, 2D vector graphics, UI compositors), which makes the problem
a realistic stand-in for a much larger class of rendering workloads.

\subsection{Computational Challenges}

A pixel $(i,j)$ belongs to circle $k$ if its center $(i+0.5,\,j+0.5)$ satisfies
$dx^2+dy^2 \le r_k^2$. In the naive formulation every one of the $H\times W$
pixels must be tested against every one of the $N$ circles, giving
$O(H\cdot W\cdot N)$ work per frame. Even after restricting each circle to its
axis-aligned bounding box, the workload remains large and highly
\emph{irregular}: circles vary enormously in radius (a few pixels up to
$\sim\!12\%$ of the image side), so the amount of work associated with
different pixels is not uniform. This irregularity, rather than raw arithmetic volume, is the
central challenge that the parallelization strategy has to address.

\subsection{Objectives and Scope}

The goal of the project is to explore, in a controlled way, which parallelization
and vectorization techniques are effective for this class of workload, and why.
The scope includes:
\begin{enumerate}[itemsep=1pt,topsep=2pt]
  \item \textbf{Sequential implementation:} a straightforward, single-threaded
    kernel used as the correctness and performance baseline.
  \item \textbf{Parallel optimization:} two coarse-grained multithreaded
    strategies (per-pixel-row and per-tile), plus a tile-based kernel whose
    inner loop is written to be auto-vectorized by the compiler.
  \item \textbf{Systematic micro-benchmarking:} isolating, one variable at a
    time, the effect of thread count, image resolution, circle count, tile
    size, scheduling strategy, SIMD, memory layout and weak scaling.
\end{enumerate}

%==================================================================
\section{Algorithm Description}

\subsection{Data Structure}

Circles are stored in a \emph{Structure-of-Arrays} (SoA) container
(\texttt{CircleSoA}): eight parallel, contiguous \texttt{float32} NumPy arrays
$(x, y, z, \text{radius}, r, g, b, a)$, rather than a list of per-circle
objects. This layout is cache-friendly and is the natural starting point for
vectorization, since each attribute is unit-stride in memory~\cite{robey}. Sorting by depth
is done once, up front, with a \emph{stable} mergesort, so that circles with
equal $z$ keep their original order deterministically.

\subsection{Sequential Algorithm}

The baseline kernel loops over circles from far to near. For each circle it
computes an integer bounding box clipped to the image, then scans only the
pixels inside that box, testing the circle equation and applying the ``over''
blend in place:

\begin{lstlisting}
for k in range(n):            # far -> near
    x0,y0,x1,y1 = bbox(k)     # clipped to image
    for j in range(y0, y1):
        for i in range(x0, x1):
            if inside_circle(i, j, k):
                blend_over(img[j, i], color(k))
\end{lstlisting}

This bounding-box restriction is the only optimization present in the
sequential version. The cost is therefore proportional to the total
bounding-box area of the $N$ circles rather than to $H\cdot W\cdot N$, and
the kernel writes directly into a shared image buffer, which is safe here
only because the loop is single-threaded.

\subsection{Parallelization Strategy}

Two independent opportunities for parallelism were identified:

\paragraph{Parallelizing across the image (multithreading).} Because the
final color of a pixel does not depend on the color of any other pixel
(circles are looked up, not accumulated across pixels), the image can be
partitioned into disjoint regions — rows or square tiles — and each region
processed independently by a different thread, with no shared mutable state
and therefore no locks.

The painter's algorithm also constrains how the work can be split: every
pixel must receive its circles in depth order. Parallelizing over circles
would let different threads blend onto the same pixel in an arbitrary
order, requiring locks or a reordering step. Parallelizing over pixels
keeps the order for free: each thread owns its pixels and walks the
already sorted circle list, which is why sorting is done once, before the
threads start.

\paragraph{Vectorizing the inner loop (SIMD).} Inside a tile, testing a
circle against many pixels performs the same arithmetic (subtraction,
multiplication, comparison, blend) on independent data. If that inner loop is
written without early-exit branches and with a small, contiguous, per-tile
buffer, the compiler's auto-vectorizer can turn it into SIMD instructions
that process several pixels per cycle.

\paragraph{Flynn's taxonomy.} The two opportunities correspond to two
classes of Flynn's taxonomy. Multithreading is \emph{MIMD} (Multiple
Instruction, Multiple Data): each thread runs on its own core with its own
instruction stream, on its own tiles, and may be culling one tile while
another thread is blending pixels of a different one. Vectorization is
\emph{SIMD} (Single Instruction, Multiple Data): a single instruction
operates on several pixels at once, all following the same path. The four
kernels therefore cover every combination: \texttt{seq} is SISD,
\texttt{pixels} and \texttt{tiles} are MIMD only, and \texttt{simd} on
several threads combines MIMD across cores with SIMD within each core.

\section{Parallel Implementation}

Four rendering kernels are implemented and compiled just-in-time with Numba, which
generates native code through LLVM
(\texttt{@njit}); the three parallel ones run on a pool of Python threads
on the free-threaded build of Python 3.14 (\S\ref{sec:nogil}). They are referred to as \texttt{seq},
\texttt{pixels}, \texttt{tiles} and \texttt{simd}, and all four are required to
produce the same image (up to floating-point reassociation error from
\texttt{fastmath}).

\subsection{Strategy Overview}

\begin{table}[h]
\centering
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Mode} & \textbf{Parallelism} & \textbf{Notes} \\
\midrule
\texttt{seq}    & none              & baseline, bbox scan \\
\texttt{pixels} & threads over rows   & no culling, slow \\
\texttt{tiles}  & threads over tiles  & bbox culling per tile \\
\texttt{simd}   & tiles + vector inner loop & fastest, branchless \\
\bottomrule
\end{tabular}
\caption{The four rendering kernels compared in this project.}
\label{tab:kernels}
\end{table}

\texttt{pixels} parallelizes over image rows: each
thread owns a disjoint set of rows and, for every pixel, loops over \emph{all}
$N$ circles with a cheap bounding-box rejection test. It has no spatial
culling structure, so it is included mainly as a ``multithreading alone''
reference point — it is intentionally slow.

\texttt{tiles} instead parallelizes over square tiles of the image. For each
tile, a thread-local candidate list is built once by testing which circles'
bounding boxes intersect the tile; only that (usually much smaller) candidate
set is then scanned against every pixel of the tile. Disjoint tiles mean
disjoint writes, so again no synchronization is needed.

\texttt{simd} uses the same tile/culling structure as \texttt{tiles}, but the
inner double loop over a tile's pixels is restructured for auto-vectorization:
for each candidate circle, all pixels of the tile are visited in a countable,
branch-free loop that computes a $0/1$ mask instead of using an \texttt{if},
and pixels are accumulated into small contiguous per-tile R/G/B scratch
buffers before being written back to the image once at the end:

\begin{lstlisting}
for ii in range(tw):                # vectorizable
    d2 = dx*dx + dy2                # FMA under fastmath
    m = 1.0 if d2 <= r2 else 0.0    # branchless mask
    rr[idx] = m*(psr + rr[idx]*inv) + (1-m)*rr[idx]
\end{lstlisting}

Removing the branch and keeping the accumulator arrays contiguous and small
(tile-sized) lets LLVM auto-vectorize the loop with unit-stride vector
loads/stores, and lets \texttt{fastmath=True} fuse the distance computation
into fused multiply-adds.

\subsection{Multithreading on Free-Threaded Python}
\label{sec:nogil}

CPython's Global Interpreter Lock (GIL) allows only one thread at a time to
execute Python code, so on a classic interpreter plain Python threads cannot
speed up CPU-bound work: they take turns on a single core. PEP~703 introduced
an optional \emph{free-threaded} build of CPython in which the GIL is
removed; it is experimental in Python~3.13 and officially supported in
Python~3.14 (\texttt{python3.14t})~\cite{slides}. On this build, threads
created with the standard \texttt{threading} and
\texttt{concurrent.futures} APIs run truly in parallel on different cores,
as in C or Java. Numba supports the free-threaded build since version 0.65,
so the compiled kernels can be called concurrently from several threads.

The project runs on Python~3.14t, managed with \texttt{uv}, and the
benchmark script refuses to start if the GIL is active. Running the same
code on the same interpreter with the GIL re-enabled
(\texttt{python -X gil=1}) is used as a control experiment
(\S\ref{sec:gil}).

The parallel versions are built on this mechanism. Each kernel
receives three extra arguments, \texttt{start}, \texttt{stop} and
\texttt{step}, and processes only the work units (rows for \texttt{pixels},
tiles for \texttt{tiles} and \texttt{simd}) with index \texttt{start},
\texttt{start+step}, \dots{} up to \texttt{stop}. The Python wrapper
submits the calls to a \texttt{concurrent.futures.ThreadPoolExecutor} with
$p$ workers and then waits for all of them, which acts as the final barrier.
With the default distribution, thread $k$ gets \texttt{start}$=k$,
\texttt{step}$=p$:

\begin{lstlisting}
@njit(cache=True, fastmath=True)
def kernel(img, ..., start, stop, step):
    for t in range(start, stop, step):
        ...                        # render tile t

futures = [pool.submit(kernel, *args, k, n_tiles, p)
           for k in range(p)]
for f in futures:
    f.result()                     # join
\end{lstlisting}

The pools are created once per thread count and reused, so thread creation
is not part of the measured time. With $p=1$ the kernel is called directly
on the main thread. The kernel code itself is the same as a sequential loop
over the work units; only the loop bounds change.

\paragraph{Work distribution.} Because circle radii vary widely, the amount
of work per tile is highly non-uniform (a tile with only small, sparse
circles finishes almost instantly; a tile covered by several large
overlapping circles is far more expensive). Assigning each thread one
contiguous block of tiles would give some threads all the expensive regions.
The interleaved assignment above corresponds to OpenMP's
\texttt{schedule(static,1)}: the tiles of every region of the image are
spread across all threads, so cheap and expensive tiles average out. The
load is further balanced by using many more tiles than threads, which is why
the tile size is studied explicitly in Section~\ref{sec:results}.

The same three arguments also express the other OpenMP schedules, which
are compared in Section~\ref{sec:scheduling}: \texttt{static} (one
contiguous block of $\lceil n/p\rceil$ tiles per thread),
\texttt{static,}$c$ (blocks of $c$ tiles dealt round-robin to the threads)
and \texttt{dynamic,}$c$ (blocks of $c$ tiles submitted as separate tasks:
the executor's queue hands the next block to whichever thread becomes free,
at the cost of one task submission per block).

\subsection{Synchronization}

By construction, every kernel here operates on disjoint output regions
(rows or tiles), so the renderer itself is \textbf{lock-free}: no shared
mutable accumulator is ever written by more than one thread, and no locks,
atomics or critical sections are required.

\paragraph{False sharing.} Disjoint regions do not guarantee disjoint cache
lines: two threads writing neighbouring pixels can still invalidate each
other's copy of a shared 64-byte line. Here this can only happen at region
borders. A tile row is $32\times3\times4=384$ bytes, i.e.\ six whole cache
lines, so two horizontally adjacent tiles share at most one line per pixel
row, and only when the image buffer is not 64-byte aligned; image rows of
the \texttt{pixels} kernel ($W\cdot 12$ bytes) behave the same way. In
\texttt{simd} the contention is reduced further, because each tile is
accumulated in private per-tile buffers and written to the shared image
only once, at the end. False sharing is therefore limited to a few lines
per tile and no padding was needed; the tile-size experiment
(\S\ref{sec:tile}) would show it as a penalty for very small tiles, where
borders make up a larger fraction of the writes.

\subsection{Challenges and Solutions}

\begin{itemize}[itemsep=1pt,topsep=2pt]
  \item \textbf{Thread parallelism in Python.} With the GIL, Python threads
    cannot run CPU-bound code in parallel. Using the free-threaded build of
    Python~3.14 together with a Numba version that supports it made plain
    \texttt{ThreadPoolExecutor} threads scale across cores; a control run
    with the GIL re-enabled verifies this (\S\ref{sec:gil}).
  \item \textbf{Preserving the painter's order.} Parallelizing over circles
    would require ordering the blends on every pixel. Parallelizing over
    pixels (rows or tiles) and sorting once, before the threads start, keeps
    the order without any synchronization.
  \item \textbf{Cost of the naive per-pixel kernel.} Testing every pixel
    against every circle (\texttt{pixels}) is $O(H\cdot W\cdot N)$. Per-tile
    culling (\texttt{tiles}) reduces each pixel's work to the circles that
    can actually cover it.
  \item \textbf{Getting the compiler to vectorize.} The first tiled kernel
    has an early \texttt{continue} per circle inside the pixel loop, which
    prevents auto-vectorization. Rewriting the inner loop as a countable,
    branch-free loop over a small contiguous per-tile buffer (mask
    $m\in\{0,1\}$ and a blend $m\cdot\text{new}+(1-m)\cdot\text{old}$)
    let LLVM emit SIMD code.
  \item \textbf{Load imbalance.} Circles of very different radii make the
    work per tile irregular; it is handled with the interleaved tile
    assignment, a large number of small tiles and, where useful, dynamic
    scheduling (\S\ref{sec:scheduling}).
  \item \textbf{Reaching a measurable workload.} The guideline of at least
    10\,s of sequential time required raising the circle count of the
    strong-scaling problem beyond the default range, to 60{,}000 circles.
\end{itemize}

\subsection{Data Structures and Memory Layout}

The default layout is SoA, as described above. For comparison, a
\texttt{to\_aos()} conversion produces an interleaved $(N,8)$
\emph{Array-of-Structures} layout, used only by the memory-layout benchmark
(Section~\ref{sec:memlayout}); the renderer itself never uses it internally.

\section{Experimental Setup}

\subsection{Environment}

Benchmarks were executed on a lab server with an \textbf{AMD Ryzen~5 2400G}
(x86-64, first-generation Zen, 3.6\,GHz base clock, 3.9\,GHz boost): 4
identical physical cores with simultaneous multithreading (SMT, 2 hardware
threads per core), i.e.\ 8 logical cores, and \tbd{RAM} of RAM assigned to
the VM. Each core has a private 32\,KB L1 data cache and a private
512\,KB L2 cache; the 4\,MB L3 cache is shared by all cores. The L1 size is
the one the default tile (32$\times$32 pixels, whose three per-tile R/G/B
buffers take 12\,KB) was tuned for. The CPU supports AVX2 and FMA, so the vectorized kernel
operates on 256-bit vectors of 8 \texttt{float32}; note that Zen executes
each 256-bit AVX2 instruction as two 128-bit halves. The machine runs Debian~13
as a virtual machine on Proxmox. The software stack was the free-threaded build of
Python 3.14.8 (GIL disabled), NumPy 2.5.3, Numba 0.68.0 and llvmlite 0.50.0
on Linux, with the environment managed by \texttt{uv}. The ``compiler'' is
Numba, which generates native code through LLVM~22.1 (bundled with
llvmlite) for the host CPU; all kernels use \texttt{@njit(cache=True,
fastmath=True)}, where \texttt{fastmath} allows floating-point
reassociation and FMA contraction (needed for vectorization) and
\texttt{cache} stores the compiled code on disk. Numba's own parallelism
(\texttt{parallel=True}, \texttt{prange}) and \texttt{nogil=True} are not
used: all parallelism comes from Python threads. CPU frequency scaling is
managed by the Proxmox host and cannot be disabled from inside the VM
\tbd{governor / boost status}; its effect is reduced by the warm-up runs
and by repeating each measurement.

The course guidelines~\cite{slides} ask for thread counts up to twice the
number of physical cores (here 8). The sweeps go further, up to
\textbf{16} threads, i.e.\ \emph{twice} the number of logical cores and
four times the physical ones, so that the thread-scaling experiment can also
observe oversubscription (thread count exceeding the logical core count), in
addition to normal scaling up to the core count. Unlike a hybrid CPU, all cores run at
the same speed, so the thread sweep has three clearly separated regimes:
1--4 threads (one thread per physical core), 5--8 threads (two threads
sharing the execution units of a physical core through SMT) and 9--16
threads (oversubscription). The server is shared, so benchmarks were run
while it was otherwise idle.

\subsection{Dataset}

The dataset is procedurally generated: $N$ circles with uniformly random
position, radius (scaled to image resolution), color and alpha. This is a
deliberate choice rather than a limitation — for a 2D rasterizer,
synthetically generated geometry \emph{is} the realistic workload, in the
same way standard rasterization benchmarks use synthetic scenes rather than
an external image dataset; there is no natural pre-existing dataset of
``circles with depth and alpha'' to substitute. Datasets are generated with
a fixed seed, so every run uses the same circles. For the scheduling
experiment only, a second variant draws the circle centers from a Gaussian
centered on the image (standard deviation $1/8$ of the side), which
concentrates the work in the middle tiles and makes it strongly unbalanced.

\subsection{Methodology and Parameters}

\begin{itemize}[itemsep=1pt,topsep=2pt]
  \item \textbf{Timing:} wall-clock time via \texttt{time.perf\_counter()}, with a per-configuration time budget that stops adding
    iterations once exceeded (bounding the cost of slow configurations), plus
    CPU time (\texttt{time.process\_time()}, summed across threads).
  \item \textbf{Statistics:} for every configuration the script reports the
    mean, sample standard deviation $\sigma$, minimum and maximum wall-clock
    time, an approximate 95\% confidence interval of the mean
    ($1.96\cdot\sigma/\sqrt{n}$) and the mean CPU time. Plots show the mean;
    the speedup curves of the strong-scaling experiment carry the confidence
    interval as error bars.
  \item \textbf{Warm-up:} each configuration is preceded by 2 warm-up runs
    (excluded from timing) to absorb Numba's JIT compilation cost; kernels are
    also cached to disk (\texttt{@njit(cache=True)}) across runs. The
    parallel kernels in the strong-scaling experiment use a single warm-up
    run, since each execution already takes seconds.
  \item \textbf{Iterations:} 5 timed iterations per configuration (subject to
    the time budget).
  \item \textbf{Scaling dataset:} the strong-scaling experiment (\S\ref{sec:scaling})
    deliberately uses a large problem ($2048^2$ pixels, 60{,}000 circles) so
    that the sequential baseline takes $\ge 10\,$s, as required by the
    course's benchmarking guidelines~\cite{slides} for meaningful speedup measurements.
  \item \textbf{Parameters tested:} threads 1, 2, 4, 8, 16; resolutions
    $512^2$, $1024^2$, $2048^2$; 500--8000 circles (60{,}000 for strong
    scaling); tile sides 16--256\,px; schedules \texttt{static},
    \texttt{static,}\{1, 4, 16\} and \texttt{dynamic,}\{1, 4, 16\}; SoA
    vs.\ AoS; GIL disabled vs.\ enabled.
  \item \textbf{Validation:} before any timing, the benchmark script renders
    the same scene with every kernel (\texttt{pixels}, \texttt{tiles},
    \texttt{simd} and the AoS variant, plus \texttt{simd} with the
    \texttt{static}, \texttt{static,4} and \texttt{dynamic,4} schedules)
    at the maximum thread count and compares each image with the sequential
    one. The check uses a tolerance
    of $10^{-3}$ on the maximum absolute pixel difference rather than
    bit-exact equality, since \texttt{fastmath=True} permits floating-point
    reassociation, and it stops the run if any kernel exceeds it. Two cases
    are tested: a $512^2$ image and a $1000\times700$ image, whose sides are
    not multiples of the tile size (partial tiles at the borders). The largest
    difference measured was \tbd{$\sim\!10^{-7}$}, i.e.\ float32 rounding.
\end{itemize}

With \texttt{static} each thread receives a contiguous band of tile rows,
so the threads that get the middle of the image do most of the work while
the others finish early. Chunk size interacts with the image geometry: with
32 tiles per row, 8 threads and chunks of 4 tiles, $8\cdot4=32$, so each

and \texttt{static,16} do not have this alignment. \texttt{dynamic}
balances the load at run time, regardless of where the work is, at the cost
of one task submission per chunk: with chunk 1 this overhead is paid 1024
times per frame, which is why \tbd{dynamic,1 vs.\ dynamic,4/16}.

\subsection{Effect of SIMD (Scalar vs.\ Vectorized)}

To isolate the contribution of vectorization from thread count,
Figure~\ref{fig:simd} compares \texttt{tiles} (scalar inner loop) against
\texttt{simd} (vectorized inner loop) across the same thread sweep (1--16),
at fixed resolution and circle count. At every thread count \texttt{simd} is
faster: \tbd{X}$\times$ at $p{=}1$ (\tbd{ms} vs.\ \tbd{ms}) and still
\tbd{X}$\times$ at $p{=}16$ (\tbd{ms} vs.\ \tbd{ms}). A 256-bit AVX2
vector holds 8 \texttt{float32} lanes, but first-generation Zen splits each
256-bit operation into two 128-bit halves, so per cycle it processes about as
many lanes as 128-bit SSE (4 \texttt{float32}). \tbd{comment on how the
measured ratio compares with this}. In Flynn's terms, this experiment
separates the two forms of parallelism: at $p{=}1$ \texttt{tiles} is SISD and
\texttt{simd} is SIMD only; along the thread axis \texttt{tiles} is MIMD
only, while \texttt{simd} combines MIMD and SIMD. This confirms
that vectorization and multithreading are two genuinely separate levers on
performance, and that neither substitutes for the other.

\subsection{Memory Layout: SoA vs.\ AoS}
\label{sec:memlayout}

Figure~\ref{fig:memlayout} compares the default SoA layout against an
interleaved AoS layout for the otherwise-identical \texttt{tiles} kernel.
The \texttt{tiles} kernel was chosen over \texttt{simd} on purpose: in
\texttt{tiles}, circle attributes are read inside the per-pixel loop (for
every candidate circle at every pixel), so it is the kernel most sensitive to
how circles are laid out in memory. In \texttt{simd}, instead, each circle's
attributes are loaded once per tile, before the vectorized loop, which then
only touches the per-tile R/G/B buffers; since SIMD there works across pixels,
not across circles, the circle layout would have almost no effect.
\tbd{SoA vs.\ AoS times at 512$^2$, 1024$^2$, 2048$^2$ and whether either
layout wins consistently}.
% Sull'M2 nessuno dei due vinceva in modo consistente (differenze 6-15% di
% segno alterno): se il server conferma, la frase sotto resta valida.
This is expected for this workload: although the attributes are read for
every candidate circle at every pixel, the access goes through the candidate
list (an indirect, gather-like access, $k=\texttt{cand}[c]$), not a
unit-stride stream over the whole array, and the candidates of a tile are few
enough that their attributes stay in L1 across the pixels of the tile in
either layout. The unit-stride advantage of SoA is therefore largely hidden,
and the memory-layout choice
matters far less here than it would for a bulk, streaming numerical kernel.

\subsection{GIL vs.\ Free-Threading}
\label{sec:gil}

To verify that the measured speedup really comes from the absence of the
GIL, the \texttt{simd} kernel ($1024^2$ image, 4000 circles) is timed over
the same thread sweep (1--16) in two subprocesses launched with the
\emph{same} free-threaded interpreter: one with \texttt{-X gil=0}
(free-threading, the configuration used everywhere else) and one with
\texttt{-X gil=1} (GIL re-enabled at startup). Code, data, interpreter and
machine are identical; only the GIL changes. The benchmark script also
checks, inside each subprocess, that the GIL is actually in the requested
state.

The kernels are compiled without Numba's \texttt{nogil=True}, so with the
GIL enabled a thread holds the lock for the whole duration of its kernel
call and the other threads wait: they run one at a time, and no speedup is
expected. Figure~\ref{fig:gil} confirms this: \tbd{speedup with the GIL
stays at about X$\times$ for every thread count, while without the GIL it
reaches Y$\times$ at p threads}.
% DA VERIFICARE: se con il GIL lo speedup scende sotto 1 con molti thread,
% citarlo (costo del passaggio del GIL tra i thread).
This shows that the parallelism measured in this report is due to the
free-threaded build of CPython, not to the compiled code releasing the GIL
on its own.

\subsection{Comparison with Amdahl's and Gustafson's Laws}

Amdahl's law~\cite{amdahl} bounds the speedup on $p$ threads as
$S(p)=1/\bigl(f+(1-f)/p\bigr)$, where $f$ is the fraction of the run that
cannot be parallelized. In the \texttt{simd} wrapper the only serial work is
allocating the image and sorting the circles by $Z$: about \tbd{ms} out of the
\tbd{s} single-thread run on the strong scaling workload, so $f\approx$\tbd{f}.
With this $f$, Amdahl predicts $S(8)\approx$\tbd{} and $S(16)\approx$\tbd{}
relative to \texttt{simd} on one thread. The measured values
(Table~\ref{tab:scaling}) are \tbd{values at 8 and 16 threads}. The Karp--Flatt metric
$e=\bigl(1/S(p)-1/p\bigr)/\bigl(1-1/p\bigr)$,
which
estimates the serial fraction from the measured speedup, gives
$e=$\tbd{} for $p=2,4,8,16$.
% DA RISCRIVERE: se e cresce con p, il limite non è il codice seriale ma un
% overhead che aumenta con i thread. Sul Ryzen le cause candidate sono:
% SMT da 5 thread in poi (due thread per core condividono le unità di
% esecuzione) e oversubscription oltre 8. Niente core eterogenei, niente
% thermal throttling (era specifico del MacBook Air).
\tbd{interpretation of $e$: SMT from 5 threads on, oversubscription beyond 8}.

Gustafson's law~\cite{robey} describes the weak scaling case, where the
problem grows with $p$: the scaled speedup is $S(p)=p-f\,(p-1)$, so with
$f\approx$\tbd{f} the efficiency should stay close to 1. \tbd{comparison with
the measured weak scaling efficiency (Fig.~\ref{fig:weak})}.

\subsection{Bottleneck Analysis}

Taken together, the experiments point to two dominant, largely independent
limits on performance:

\begin{itemize}[itemsep=1pt,topsep=2pt]
  \item \textbf{Physical core count, SMT and oversubscription.}
    \tbd{what strong and weak scaling show in the three regimes: 1--4 threads
    (one per physical core), 5--8 threads (SMT siblings competing for the
    same execution units, which a compute-bound vectorized kernel already
    keeps busy) and beyond 8 threads (oversubscription of the 8 logical
    cores, scheduling overhead only)}.
  \item \textbf{Load imbalance from circle-size variance}, which is exactly
    why the interleaved tile distribution and tile-size tuning matter
    more than memory-layout choices for this workload: unlike a dense
    numerical kernel, the bottleneck here is uneven \emph{work} distribution
    across parallel units, not memory bandwidth or cache locality (as
    confirmed by the lack of a consistent SoA/AoS difference).
\end{itemize}

\subsection{Limitations}

\begin{itemize}[itemsep=1pt,topsep=2pt]
  \item \textbf{Small machine.} With 4 physical cores the scaling study
    covers only a short range of real parallelism; beyond 4 threads the
    results measure SMT and oversubscription rather than additional cores.
  \item \textbf{Virtualized, shared environment.} The server is a Proxmox VM
    shared with other users: frequency scaling and the scheduling of the
    virtual CPUs are controlled by the host and can add noise, which the
    warm-up, repetitions and confidence intervals only partially absorb.
  \item \textbf{Synthetic data.} Circles are uniformly distributed except
    in the scheduling experiment; real scenes may be more clustered, which
    would make load balancing more important.
  \item \textbf{Serial part.} Sorting and image allocation remain
    sequential (\S\ref{sec:results}, Amdahl); for much larger circle counts
    the sort would also need to be parallelized.
  \item \textbf{Indirect control of vectorization.} SIMD code is produced by
    Numba/LLVM auto-vectorization, not by explicit intrinsics: small changes
    to the inner loop can silently disable it, and the vector width is
    chosen by the compiler.
  \item \textbf{Fixed tile size.} One tile size (32\,px) is used for every
    image; dense or sparse regions might benefit from different sizes.
\end{itemize}

\section{Conclusions}

This project implemented and systematically benchmarked a CPU-parallel 2D
circle rasterizer, combining coarse-grained multithreading (Python threads
on free-threaded Python~3.14, over image tiles) with fine-grained SIMD vectorization
(a branchless, auto-vectorizable inner loop). The tiled, vectorized kernel
reaches a maximum speedup of \tbd{S$_{\max}$} over the sequential
baseline on a 4-core / 8-thread AMD Ryzen~5 2400G, with vectorization alone contributing
roughly \tbd{X$\times$} independently of thread count. Culling
(tile-based candidate lists) and vectorization proved to be complementary,
additive optimizations rather than substitutes for one another. A dedicated
tile-size sweep identified small tiles (32~px for \texttt{simd}) as the sweet spot for this workload,
and, since tiles are disjoint, the renderer needs no synchronization at all.
Memory layout (SoA vs.\ AoS) had a comparatively minor effect,
consistent with a workload whose bottleneck is irregular per-tile work rather
than memory bandwidth. \tbd{one-sentence summary of strong and weak scaling
across the physical-core, SMT and oversubscription regimes}.

\textbf{Best configuration found:} the \texttt{simd} kernel with SoA
layout, 32$\times$32 tiles, \tbd{schedule} scheduling and \tbd{p}
threads, which renders the 60{,}000-circle $2048^2$ scene in \tbd{ms}
instead of the \tbd{T$_{\text{seq}}$}\,s of the sequential kernel
(speedup \tbd{S$_{\max}$}). On a uniform scene the default interleaved
assignment (\texttt{static,1}) is \tbd{as good as / slightly worse than}
dynamic scheduling; on unbalanced scenes \tbd{schedule} is preferable.

Future work could explore spatial acceleration structures (e.g.\ a
tile-local BVH or grid over circles for very high circle counts), GPU
offload of the tile-based kernel, and adaptive tile sizing driven by local
circle density rather than a single fixed tile size.
